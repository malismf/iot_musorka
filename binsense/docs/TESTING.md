# Проверки и тесты

Что можно проверить, не имея железа под рукой, и как убедиться, что система
работает целиком.

## Тесты прошивки (без платы)

```bash
cd firmware/hosttest
./run.sh
```

- 51 проверка чистой логики: медиана замеров, разбор кадра UART-датчика с
  контрольной суммой, расчёт заполненности (включая случаи «нет калибровки» и
  «калибровка некорректна»), выбор интервала замеров, правило
  отправки, повторный замер при скачке уровня, собственный разбор и сборка
  JSON;
- пробная сборка всех файлов прошивки с заглушками Arduino/ESP8266 — и
  основного варианта, и варианта с HC-SR04.

Настоящая сборка для платы — `cd firmware && pio run` (окружения `esp8266`
и `esp8266_hcsr04`).

Нужен только `g++`; другой компилятор — через переменную `CXX`
(`CXX=clang++ ./run.sh`).

## Тесты сервера

Нужна работающая база PostgreSQL (проще всего — из `docker compose`).

```bash
cd backend
pip install -r requirements-dev.txt
createdb binsense_test   # или: docker compose exec db createdb -U binsense binsense_test

TEST_DATABASE_URL=postgresql://binsense:ПАРОЛЬ@localhost:5432/binsense_test \
    python -m pytest
```

38 тестов:

| Файл | Что проверяет |
|---|---|
| `tests/test_rules.py` | правила событий (заполнен, вывезен), состав настроек устройства, маршруты, хеширование паролей и кодов привязки, JWT |
| `tests/test_api.py` | регистрация, полный доступ любого пользователя, очистка событий, подготовка устройства, привязка по коду (включая блокировку перебора), изменение настроек с ростом версии, история, события, журнал действий |
| `tests/test_ingest.py` | приём телеметрии (в том числе от старой прошивки с полями крышки), дубликаты QoS 1, подсчёт потерь по `seq`, события, калибровка, определение «нет связи», срочная эскалация, очистка старых данных |

Обращения к MQTT в тестах подменяются заглушкой, поэтому брокер не нужен.

## Проверка всей системы без устройств

```bash
docker compose up -d --build
docker compose --profile demo up -d emulator
```

Эмулятор регистрируется на сервере теми же запросами, что и настоящее
устройство, получает собственную учётную запись MQTT, подписывается на свои
настройки и публикует телеметрию. Проверяется вся цепочка: брокер → ingestor →
база → API → карта.

## Проверка с настоящей платой

Сервер на ноутбуке, плата подключается к нему по Wi-Fi — пошагово в
[LOCAL_TEST.md](LOCAL_TEST.md).

## Проверка вручную

```bash
# посмотреть поток сообщений от устройств
docker compose exec mqtt mosquitto_sub -u "$MQTT_ADMIN_USER" -P "$MQTT_ADMIN_PASSWORD" -t 'bins/#' -v

# отправить телеметрию от имени устройства (учётные данные — из provision.py)
mosquitto_pub -h ВАШ_ДОМЕН -p 1883 -u bin-a1b2c3 -P ПАРОЛЬ \
  -t bins/bin-a1b2c3/telemetry -q 1 \
  -m '{"seq":1,"boot":1,"fill":85,"dist_mm":360,"rssi":-60,"wake":"timer"}'

# убедиться, что чужой топик недоступен (сообщение будет отброшено брокером)
mosquitto_pub -h ВАШ_ДОМЕН -p 1883 -u bin-a1b2c3 -P ПАРОЛЬ \
  -t bins/bin-other/telemetry -q 1 -m '{"fill":1}'
```

## Полевая проверка устройства

Перед сдачей полезно оставить устройство на реальном контейнере на 5–7 дней и
проверить:

- сколько сообщений потеряно (Grafana, панель «Потеряно сообщений»);
- задержку доставки и время подключения к Wi-Fi и брокеру (там же);
- как меняется RSSI в течение суток;
- появляется ли конденсат внутри корпуса;
- не сбивается ли калибровка после нескольких вывозов.
