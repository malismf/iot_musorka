Как модули системы разговаривают друг с другом (пункты 2 и 3 задания).

| Участники | Протокол | Где описано |
|---|---|---|
| Устройство ↔ сервер | MQTT 3.1.1 поверх Wi-Fi, QoS 1 | этот файл, `docs/asyncapi.yaml` |
| Датчик ↔ микроконтроллер | UART 9600 (A02YYUW / JSN-SR04T) | раздел 5 |
| Периферия ↔ микроконтроллер | цифровой вход, ШИМ, АЦП | `hardware/WIRING.md` |

| Grafana ↔ база | PostgreSQL wire protocol, роль только для чтения | `infra/grafana` |

## 1. MQTT: устройство и сервер

Формальное описание — `docs/asyncapi.yaml` (AsyncAPI 2.6, открывается в
[studio.asyncapi.com](https://studio.asyncapi.com)).

### Топики

```
bins/<id>/telemetry    устройство → сервер   QoS 1
bins/<id>/event        устройство → сервер   QoS 1
bins/<id>/config       сервер → устройству   QoS 1, retained
```

`<id>` — идентификатор вида `bin-a1b2c3`: префикс и последние три байта
MAC-адреса. Он же служит логином MQTT и client id.

### Телеметрия

```json
{
  "seq": 1532, "boot": 884213, "ts": 1790000000,
  "fill": 72, "dist_mm": 454, "rssi": -67, "wake": "timer",
  "wifi_ms": 1210, "mqtt_ms": 260,
  "fw": "2.0.0", "hw": "esp8266-a02yyuw", "cfg_ver": 3
}
```

- `fill` — заполненность в процентах; `null`, если устройство не откалибровано;
- `seq` — счётчик сообщений: по разрывам сервер считает потери;
- `boot` — случайное число, генерируемое при включении питания: отличает
  перезагрузку (счётчик начался заново) от настоящей потери сообщений;
- `ts` — время измерения по часам устройства; сервер сравнивает его со своим
  временем и получает задержку доставки, она видна в Grafana;
- `wake` — что разбудило устройство: `timer`, `button`, `boot`, `setup`;
- `cfg_ver` — версия применённых настроек, так сервер узнаёт, что они дошли.

### События

```json
{"type": "calibrated", "empty_mm": 982, "full_mm": 250}
{"type": "error", "code": "SENSOR_TIMEOUT"}
{"type": "hello", "fw": "2.0.0", "hw": "esp8266-a02yyuw", "reset": "POWERON"}
```

### Настройки

```json
{
  "ver": 3, "claimed": true,
  "interval_s": 900, "heartbeat_s": 7200,
  "full_interval_s": 300, "night_interval_s": 1800,
  "night": [23, 7], "tz": "MSK-3",
  "full_pct": 80, "delta_pct": 3, "samples": 7,
  "empty_mm": 982, "full_mm": 250
}
```

Сообщение публикуется с флагом **retain**: устройство получает последнюю
версию настроек сразу после подписки — после включения или переподключения, —
даже если настройки поменяли, пока оно было без связи. Пока связь есть,
новые настройки приходят и применяются сразу. Применяются только
настройки с большей версией; применённую версию устройство возвращает в
`cfg_ver`, и в карточке появляется отметка «настройки применены».

### Решения, которые стоит объяснить на защите

**Почему не Last Will.** Статус «нет связи» вычисляет сервер: если данных нет
дольше `heartbeat_s × 1.5`, устройство помечается офлайн и создаётся событие.
Так статус не зависит от брокера: он верен и после перезапуска Mosquitto, и
когда устройство на связи, но перестало присылать данные.

**Почему QoS 1.** Устройство считает данные отправленными, только когда
брокер подтвердил приём; иначе отправит их при следующем замере. На стороне сервера ingestor подписан с `clean_session=false`, поэтому
сообщения, пришедшие во время его перезапуска, брокер доставит позже.
Дубликаты (QoS 1 допускает повторную доставку) отсекаются уникальным индексом
по `(device_id, boot_id, seq)`.

**Почему отправляем не каждое измерение.** Устройство измеряет часто, а
отправляет, только если заполненность изменилась больше чем на `delta_pct`,
произошло событие или истёк `heartbeat_s`. В базе и на графиках остаются
изменения, а не тысячи одинаковых точек.

### Разграничение доступа

Mosquitto работает с плагином dynamic-security. При подготовке устройства
сервер создаёт клиента с логином `bin-a1b2c3` и роль `dev-bin-a1b2c3`:

| Действие | Топик |
|---|---|
| публикация | `bins/bin-a1b2c3/telemetry` |
| публикация | `bins/bin-a1b2c3/event` |
| подписка | `bins/bin-a1b2c3/config` |

Попытка писать в чужой топик брокером отбрасывается (устройство при этом не
получает ошибку — сообщение просто не доходит). Анонимные подключения
запрещены.

## 2. Взаимодействие сервисов внутри сервера

```
mosquitto ──MQTT──► ingestor ──SQL──► PostgreSQL ◄──SQL── api ──HTTP/WS──► браузер
                        │                  ▲                   ▲
                        └──HTTPS──► Telegram│                   │
                                            └── LISTEN/NOTIFY ──┘
```

`ingestor` и `api` — разные процессы. Чтобы карта обновлялась мгновенно,
ingestor после записи телеметрии выполняет `pg_notify('binsense_ws', …)`, а api
слушает этот канал и рассылает сообщение по WebSocket. Отдельный брокер
(Redis) для этого не нужен.

## 3. REST API и WebSocket

Базовый адрес: `https://<домен>/api`. Авторизация — заголовок
`Authorization: Bearer <JWT>`, токен выдают `/auth/login` и `/auth/register`.
Полное описание: `/api/docs` (Swagger) и `docs/openapi.json`.

| Метод | Назначение |
|---|---|
| `POST /auth/register`, `/auth/login` | регистрация и вход |
| `GET /me`, `PATCH /me` | профиль и настройки уведомлений |
| `POST /me/telegram-link` | одноразовая ссылка для привязки Telegram |
| `GET /devices` | список устройств с последними значениями (для карты) |
| `GET /devices/{id}` | карточка устройства |
| `POST /devices/claim` | привязка по коду из `provision.py` |
| `PATCH /devices/{id}` | название, место, пороги, калибровка |
| `DELETE /devices/{id}/claim` | отвязка |
| `GET /devices/{id}/telemetry` | история, `bucket=raw\|5m\|1h\|1d` |
| `GET /devices/{id}/events` | события устройства |
| `GET /devices/{id}/forecast` | прогноз заполнения |
| `GET /events`, `POST /events/{id}/ack` | лента событий и подтверждение |
| `GET /stats/overview` | сводка для панели |
| `GET /route` | маршрут по заполненным контейнерам |
| `POST /admin/devices` | подготовка устройства (учётка MQTT + код привязки) |
| `GET /admin/users`, `PATCH /admin/users/{id}` | пользователи и роли |
| `GET /admin/audit` | журнал действий |
| `GET /config/public` | центр карты, имя бота (доступно без авторизации) |
| `GET /health` | состояние сервиса |

WebSocket: `wss://<домен>/api/ws?token=<JWT>`. Сервер присылает:

```json
{"type": "telemetry", "device": { …карточка устройства… }}
{"type": "event", "event": { …событие… }}
{"type": "event_ack", "event_id": 42, "acked_by": "Иван"}
```

Клиент раз в 30 секунд отправляет `ping` и получает `{"type":"pong"}`.

### Роли

| Роль | Права |
|---|---|
| `admin` | всё, включая подготовку устройств, пользователей и журнал |
| `dispatcher` | привязка и настройка устройств, подтверждение событий |
| `driver` | просмотр карты и списка, подтверждение событий |

## 4. Telegram

Уведомления отправляет ingestor обычным HTTPS-запросом к Bot API
(`sendMessage` с `inline_keyboard`), а команды и нажатия кнопок обрабатывает
отдельный сервис `bot` на aiogram. Привязка чата к аккаунту — через
одноразовый токен: приложение выдаёт ссылку `https://t.me/<bot>?start=<token>`,
бот проверяет токен и сохраняет `chat_id`.

Команды: `/status`, `/full`, `/bins`, `/events`, `/unlink`, `/help`.
Кнопка «Принято» под уведомлением подтверждает событие тем же действием, что
и кнопка в веб-приложении.

## 5. Периферия и микроконтроллер

| Устройство | Способ взаимодействия |
|---|---|
| Ультразвуковой датчик A02YYUW / JSN-SR04T | проводной протокол UART (программный на D5/D6), 9600 бод |
| HC-SR04 | цифровой выход Trig + измерение длительности импульса Echo |
| Кнопка | цифровой вход с подтяжкой, дребезг подавляется в прошивке |
| RGB-светодиод | ШИМ (три канала, analogWrite) |
| Зуммер | цифровой выход через транзисторный ключ |
| Сеть | Wi-Fi 802.11 b/g/n, 2.4 ГГц |

Кадр UART-датчика — четыре байта: `0xFF`, старший байт расстояния, младший
байт, контрольная сумма `(0xFF + H + L) & 0xFF`. Разбор и проверка суммы:
`firmware/src/measure.cpp`, тесты — `firmware/hosttest/test_logic.cpp`.
